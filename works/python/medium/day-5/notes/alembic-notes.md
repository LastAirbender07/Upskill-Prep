# Alembic Notes

## What is Alembic

Alembic is a database migration tool for SQLAlchemy. It tracks schema changes over time using
versioned migration files — similar to how git tracks code changes.

Without Alembic, you'd have to manually write `CREATE TABLE`, `ALTER TABLE` SQL every time your
schema changes, and keep track of what's been applied to which database.

---

## How it works

```
alembic.ini          — configuration file (script location, logging)
alembic/env.py       — the script that runs during every migration command
alembic/versions/    — one .py file per migration, chained together
```

Each migration file has:
- `revision` — unique ID for this migration
- `down_revision` — ID of the previous migration (forms the chain)
- `upgrade()` — SQL to apply this change
- `downgrade()` — SQL to undo this change

Alembic stores the currently applied revision in a table called `alembic_version` in your DB.
When you run `alembic upgrade head`, it checks that table, finds where you are, and runs only
the migrations you haven't applied yet.

---

## Key commands

```bash
# generate a new migration by comparing models to DB
alembic revision --autogenerate -m "description of change"

# apply all pending migrations
alembic upgrade head

# apply one migration forward
alembic upgrade +1

# roll back one migration
alembic downgrade -1

# roll back everything
alembic downgrade base

# see current state
alembic current

# see full history
alembic history

# see what SQL would run without actually running it
alembic upgrade head --sql
```

## env.py — the important file

This is the glue between Alembic and your application. Three things it must do:

### 1. Set the database URL dynamically
```python
from dotenv import load_dotenv
load_dotenv()

from app.core.settings import settings
config.set_main_option("sqlalchemy.url", settings.SQLALCHEMY_DATABASE_URL)
```
Never hardcode credentials in `alembic.ini`. Override via `config.set_main_option()` at runtime.

### 2. Set target_metadata
```python
from app.database.base import Base
target_metadata = Base.metadata
```
This is what autogenerate compares against the live DB. Without it, Alembic generates empty migrations.

### 3. Import every model
```python
from app.models.users import User            # noqa: F401
from app.models.products import Product      # noqa: F401
# ... all models
```
SQLAlchemy only knows about a table when its model class has been imported. If you skip a model,
that table won't appear in autogenerated migrations. The imports look unused to linters — that's
why `# noqa: F401` suppresses the warning.

## autogenerate — what it can and cannot detect

### Can detect automatically
- New tables
- Dropped tables
- New columns
- Dropped columns
- Column type changes
- New indexes
- Dropped indexes
- New constraints (UniqueConstraint, CheckConstraint)

### Cannot detect automatically
- Renaming a table (sees it as drop + create)
- Renaming a column (sees it as drop + create)
- Changes inside stored procedures or triggers
- Data migrations (moving/transforming data)

When Alembic can't detect something, you write the migration manually using `op.*` functions.

## Manually editing a generated migration

Always open and read the generated file before running it. Alembic adds a comment:
```python
# ### commands auto generated by Alembic - please adjust! ###
```

Common reasons to edit:
- Rename detected as drop+create — fix it to use `op.rename_table()` or `op.alter_column()`
- Adding a non-nullable column to a table with existing data — need to add a default or backfill first
- Custom ordering needed

---

## Migration for a non-nullable column (tricky case)

If you add a `NOT NULL` column to a table that already has rows, the DB will reject it —
existing rows have no value for the new column.

The pattern:
```python
def upgrade():
    # 1. add as nullable first
    op.add_column('orders', sa.Column('region', sa.String(50), nullable=True))

    # 2. backfill existing rows
    op.execute("UPDATE orders SET region = 'unknown' WHERE region IS NULL")

    # 3. now enforce NOT NULL
    op.alter_column('orders', 'region', nullable=False)
```

This is one of the migration scenarios in requirements.md — you'll practice it.

---

## Migration for adding an index after the fact

Simulates discovering a slow query and adding an index without rebuilding the table:
```python
def upgrade():
    op.create_index('ix_orders_status', 'orders', ['status'], unique=False)

def downgrade():
    op.drop_index('ix_orders_status', table_name='orders')
```

---

## Migration for renaming a column

Alembic autogenerate sees a rename as drop+create (data loss). Fix it manually:
```python
def upgrade():
    op.alter_column('users', 'full_name', new_column_name='name')

def downgrade():
    op.alter_column('users', 'name', new_column_name='full_name')
```

## alembic_version table

Alembic creates this table automatically in your database:
```sql
SELECT * FROM alembic_version;
--  version_num
-- -------------
--  387911d9fc1c
```

It stores the revision ID of the last applied migration. When you run `upgrade head`, Alembic
reads this, walks the chain from there to `head`, and runs only the missing ones.

Do not manually edit this table.

---

## Branching (good to know, don't need now)

If two developers add migrations independently off the same revision, Alembic creates two branches.
You'll see an error like "Multiple head revisions" when running upgrade.

Fix with:
```bash
alembic merge heads -m "merge branches"
```

This creates a merge migration that has two `down_revision` values.

---

## What alembic.ini should look like

Keep the URL as a placeholder — override it in env.py:
```ini
sqlalchemy.url = postgresql://user:pass@localhost/dbname
```

The real URL comes from your `.env` file via Settings, never from this file.
