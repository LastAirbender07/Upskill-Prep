### Model configuration with `model_config = ConfigDict(from_attributes=True)`

model_config = ConfigDict(from_attributes=True): This line creates a configuration dictionary for the model, allowing it to be initialized from attributes. The `from_attributes=True` parameter indicates that the model can be constructed using its attributes directly.

eg: say we have a ORM model:
user = User(
    id=1,
    name="Jayaraj",
    email="jayaraj@example.com"
)

Its data is accessed like:

user.id
user.name
user.email

and say the pydantic schema is like:

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

Pydantic normally expects something dictionary-like:

{
    "id": 1,
    "name": "Jayaraj",
    "email": "jayaraj@example.com"
}

but with `model_config = ConfigDict(from_attributes=True)`, you can create a Pydantic model directly from the ORM model's attributes without needing to convert it to a dictionary first. This allows for more seamless integration between your ORM models and Pydantic schemas.

so we can do:
response = UserResponse.model_validate(user)

and effectively read:

user.id
user.name
user.email

instead of requiring:

user["id"]
user["name"]
user["email"]

### Field
- **Field**: In Pydantic, a field refers to the attributes defined in the Pydantic model class. These fields are used for data validation and serialization. For example, in the `UserResponse` model, `id`, `name`, and `email` are fields.

### why does some schemas are defined as `Base`, `Create`, `Update`, `Response`- and model_config = ConfigDict(from_attributes=True) is used in `Response` schemas?

In many applications, especially those following RESTful API design principles, different schemas are defined for different purposes to handle various operations on the data. Here's a breakdown of why schemas are often defined as `Base`, `Create`, `Update`, and `Response`, and why `model_config = ConfigDict(from_attributes=True)` is used in `Response` schemas:

- **Base Schema**: This schema contains the common fields shared by multiple other schemas. It serves as a foundation for other schemas to inherit from, reducing code duplication.
- **Create Schema**: This schema is used when creating a new record. It typically includes the fields required for creation but may exclude fields like `id` or `created_at` that are generated by the database.
- **Update Schema**: This schema is used when updating an existing record. It usually makes all fields optional to allow partial updates.
- **Response Schema**: This schema is used when returning data from the API. It often includes all fields, including those generated by the database. The `model_config = ConfigDict(from_attributes=True)` setting allows the response schema to be populated directly from ORM model instances, making it easier to integrate with the database layer.
